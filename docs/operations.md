# 運用の手引き (控え・戻し・点検・版上げ)

読み手は、会社のシステムを預かる人です。プログラムは書けなくてかまいません。

VPS を 1 台借りて、2 社分の置き場を https で立て、取引先とつなぐまでの手順は [vps.md](vps.md) にあります。この文書は、立てた後の毎日の運用です。

## この文書は何か

この文書は、`seizou new` で立ち上げた会社のシステムを、毎日安心して使い続けるための手順です。毎日の控え (バックアップ) の取り方、壊したときの戻し方、立ち上げの確かめ (点検) の読み方、seizou の版を上げる手順を書きます。

命令は、置き場 (`seizou new` が作ったフォルダ。既定は `~/seizou-sites/<会社の id>/`) に移ってから、`<python> manage.py …` の形で打ちます。`<python>` は、置き場の README の「起動」の 1 行に出てくる Python と同じ物です (例 `<seizou を clone した場所>/.venv/bin/python`)。

## 毎日の控え (バックアップ)

次の命令で、控えを 1 つ取ります。

```
<python> manage.py seizou_backup
```

この命令は、置き場の `backups/` の下に、日時の名前のフォルダ (例 `backups/20261103-020000/`) を 1 つ作ります。中身は次の 5 つです。

- データベースの写し (SQLite は `db.sqlite3`、PostgreSQL は `db.pgdump`)
- 上げたファイル (図面・添付・マニュアルの画像) の写し `media/`
- 会社の答え `answers.yaml` の写し (置き場にあるときだけ)
- 中身の一覧 `backup.json` (取った日時・データベースの種類・会社の id・seizou の版・上げたファイルの数・各ファイルの sha256・当てた migration)
- 会社の作り込みの写し `site/` (`settings.py`・`manage.py`・`checks.py`・`fields/`・`templates/`・`static/`・`manual/`・`deploy/`・`.claude/`・`CLAUDE.md`・`AGENTS.md`・`README.md`。`.env` とデータベースと上げたファイルは入れない)

命令は、写したデータベースを `integrity_check` で確かめ、通らなければ控えを残さずに止まります (PostgreSQL の写しは確かめません)。

`.env` (鍵) は控えに入りません。`.env` だけは、控えとは別の安全な場所に人の手で写してください。中身を人に見せたり、メールやチャットに貼ったりしません。

控えのフォルダは、同じ PC が壊れたときに備えて、別の PC か外の記録装置にも写してください。遠くの置き場へ自動で控える仕組みはありません。置き場を変えるときは `--to <フォルダ>` を付けます。

毎晩 2 時に自動で控えるには、cron に次の 1 行を足します (置き場と Python の道は例です。自分の物に置き換えてください)。

```
0 2 * * * cd /path/to/site && /path/to/.venv/bin/python manage.py seizou_backup --keep 30 >> backups/backup.log 2>&1
```

`--keep 30` を付けると、命令は新しい控えの確かめが通った後に、名前の日時が 30 日より古い控えを消し、消した名前を 1 行ずつ書きます。戻す前の退避 (`<日時>-before-restore`) は消しません。新しい控えが失敗した夜は、何も消しません。

手で消すときは、先に `<python> manage.py seizou_restore --list` で一覧を見てから消します。30 日より前の控えを消す 1 行の例です。

```
find /path/to/site/backups -maxdepth 1 -type d -name '20??????-??????*' -mtime +30 -exec rm -r {} +
```

毎朝 6 時に点検し、直す物があればメールで届けるには、cron に次の 1 行を足します (道は上と同じく例です)。

```
0 6 * * * cd /path/to/site && /path/to/.venv/bin/python manage.py seizou_doctor --mail >> backups/doctor.log 2>&1
```

メールを送るには、設定の画面の「メールの知らせ」の送り方が要ります。宛先は、「試しに送る」と同じ差出人のアドレスです。良い行だけの朝は、メールを送りません。送れなかったときは、その訳を `backups/doctor.log` に 1 行書きます。外の見張りの道具を使う会社は、命令の終わりの番号 1 (直す物がある) を拾えば足ります。

PostgreSQL の置き場では、PostgreSQL の命令 `pg_dump` が要ります。`pg_dump` が見つからないとき、命令は何も書かずに止まり、手で取るための 1 行を出します。

`settings.py` の `MEDIA_ROOT` が置き場そのものかその親のフォルダを指しているときは、控えに置き場の全部 (`.env` を含む) が入り、戻しが置き場ごと消すのを防ぐため、控えと戻しは何も書かず何も消さずに止まります (`seizou new` が書く `MEDIA_ROOT = BASE_DIR / "media"` では起きません)。

控えの `site/` は、戻しの命令 (`seizou_restore`) では戻しません (置き場のコードを、控えの古い物で上書きしないため)。置き場ごと失ったときは、`seizou new` で置き場を作り直し、控えの `site/` の中身をその置き場に写してから、`seizou_restore` でデータベースと上げたファイルを戻します。`.env` は、別に写しておいた物を戻します。

会社のポカよけ `checks.py` と、Claude Code の設定 `.claude/` も、控えの `site/` に入ります。`seizou new` は空の `checks.py` を作るので、置き場を作り直したときは、控えの `site/checks.py` で上書きします。v0.1.0 までの seizou で取った控えには、この 2 つが入っていません。その控えしか無いときは、別の場所に写しておいた物を戻します。

### Windows の PC で、毎晩の控えと毎朝の点検を回す

Windows には cron がありません。Windows の PC に置いた置き場では、タスク スケジューラ (Windows に入っている、決まった時刻に命令を打つ仕組み) を使います。この小節の例は、作者の手元の Windows の実機では未確認です。

置き場に `.bat` のファイルを 1 つずつ置き、タスク スケジューラからそのファイルを呼ぶ形を勧めます。`schtasks` の `/TR` に書ける字は 261 字までなので、命令を直に書くと、道が長いときに入りません。

毎晩の控えのファイル (例 `<置き場>\backup.bat`) の中身です。`<python>` は、置き場の README の「起動」の 1 行に出てくる Python です (Windows では `<seizou を clone した場所>\.venv\Scripts\python.exe` の形)。

```
@echo off
cd /d "<置き場>"
"<python>" manage.py seizou_backup --keep 30 >> backups\backup.log 2>&1
```

次の命令で、毎晩 2 時にこのファイルを呼ぶ仕事を置きます。道に空白があるときの `schtasks` の引用符の付け方も、未確認です。

```
schtasks /Create /TN "seizou 控え <会社の id>" /SC DAILY /ST 02:00 /TR "<置き場>\backup.bat"
```

毎朝の点検は、同じ形の `.bat` (例 `<置き場>\doctor.bat`) の 3 行目を `"<python>" manage.py seizou_doctor --mail >> backups\doctor.log 2>&1` にし、`/ST 06:00` で置きます。`/TN` の名前は、控えの仕事と別の名前にします。

古い控えは `--keep 30` で消えます (上の `find` の 1 行は、Windows では使えません)。PC の電源が切れている時刻には、控えも点検も回りません。置いた次の日に、`<python> manage.py seizou_restore --list` と `backups\backup.log` で、控えが取れたかを確かめてください。

## 外への写し (VPS の外へ暗号で控える)

この手順は、作者の手元では未確認です (restic と R2 で 1 回なぞるまで、この 1 文を残します)。

毎日の控えは、置き場と同じディスクの `backups/` にだけあり、暗号もかかっていません。VPS ごと失うと (借りた先の障害・誤った消し方・乗っ取り)、データベースと控えが一緒に消えます。この節は、控えのフォルダを暗号にして、VPS の外へ毎晩写す例です。seizou の命令は外へ写さないので、OS の cron から別の道具を動かします。

例は 1 つです。restic (控えを暗号にして送る道具) で、置き場の `backups/` を S3 互換の写し先 (例 Cloudflare R2) へ毎晩送ります。Dropbox の同期のフォルダや、普段は外しておく HDD を写し先にしてもかまいません。そのときは、下の `RESTIC_REPOSITORY` の値を、そのフォルダの道に変えます。どれを選ぶかは、会社が決めます。

### 写し先を作る

restic を OS に入れておきます (入れ方は restic の案内を見てください。作者は未確認)。

restic に渡す値は、置き場の `.env` に書きません。持ち主だけが読める別のファイル (例 `/srv/seizou/restic.env`。権限 600) に、次の 4 行を書きます。値は全部置き字なので、自分の物に置き換えます。

```
RESTIC_REPOSITORY=s3:https://<アカウントのID>.r2.cloudflarestorage.com/<写し先の名前>
RESTIC_PASSWORD_FILE=<合言葉のファイルの道>
AWS_ACCESS_KEY_ID=<書くだけの鍵のID>
AWS_SECRET_ACCESS_KEY=<書くだけの鍵の値>
```

`RESTIC_PASSWORD_FILE` は、restic の合言葉を 1 行だけ書いたファイルの道です (このファイルも権限 600)。`AWS_` の 2 行は、写し先で出した鍵です。

写し先は 1 度だけ作ります。`set -a` の行は、ファイルの 4 行を restic に渡す印です。

```
set -a; . /srv/seizou/restic.env; set +a
restic init
```

### 毎晩写す

上の「毎日の控え」の cron の後の時刻に、cron で写します。控えと同じ利用者の cron に、次の 1 行を足します (道は例です)。

```
30 3 * * * set -a; . /srv/seizou/restic.env; set +a; restic backup /path/to/site/backups >> /path/to/site/backups/restic.log 2>&1
```

restic に渡す道は `backups/` だけにします。置き場の全部を渡すと、`.env` が写しに入るためです。`.env` は、上の「毎日の控え」の決まりのとおり控えに入れず、restic の写しにも入れません。`.env` は人の手で VPS の外に写します (紙に書いて金庫に入れるか、暗号をかけた別の保管場所に置く)。

確かめ方: `set -a` の行の後に `restic snapshots` を打ち、写した日時の行が並ぶのを見ます。

### 合言葉と鍵の守り

cron が夜に使うので、restic の合言葉は VPS に置きます。VPS を乗っ取られると、合言葉と鍵も読まれます。そのため、写しを消されない守りは、写し先の側で作ります。

- 写し先の側で、古い版を残す設定と、決めた期間は消せないロックをかけます。R2 の設定の画面の名前と手順は未確認です。
- VPS に置く鍵は、書くだけの鍵 (消す権限の無い鍵) にします。書くだけの鍵を出せる写し先を選びます。書くだけの鍵で restic が最後まで通るかは、1 回なぞって確かめてください (作者は未確認)。
- 合言葉を失うと、写しを開けません。合言葉は紙にも書き、VPS の外の別の場所に置きます。

### 写しから戻す

VPS ごと失ったときは、[vps.md](vps.md) のとおりに新しい VPS と置き場を立て、別に写した `.env` と、`restic.env` と合言葉のファイルを戻します。続けて、写しを一時のフォルダに取り出し、次の「戻す (復元)」の段のとおりに戻します (`set -a` の行の後に打ちます)。

```
restic restore latest --target <一時のフォルダ>
<python> manage.py seizou_restore --list --dir <一時のフォルダ>/path/to/site/backups
<python> manage.py seizou_restore <控えの名前> --dir <一時のフォルダ>/path/to/site/backups
```

restic は元の道の形のまま取り出すので、一時のフォルダの下に `path/to/site/backups` の道が並びます。`seizou_restore` は、`--dir` で控えの置き場を変えられます。

失う量は、ディスクの一部の故障なら最悪 1 日分 (毎晩の控えの間) で、VPS ごと失ったときは最後に外へ写した控えの日時から後の分です。

## 取引の記録を残す期間 (目安)

seizou は、伝票と送り合った記録を消さずに残し続けます。会社が何年残すかの目安と、seizou で消せるかを、次の表にまとめます。

目安です。会社の税理士か顧問に確かめてください。

| 記録 | どこにあるか | 残す期間の目安 | seizou で消せるか |
|---|---|---|---|
| 請求書・入金 | 「請求書」の画面 | 7 年 (欠損金のある年度は 10 年) | 消せない (取り消しても行は残る) |
| 受注 | 「受注」の画面 | 7 年 (欠損金のある年度は 10 年) | 消せない (取り消しても行は残る) |
| 発注 | 「発注」の画面 | 7 年 (欠損金のある年度は 10 年)。協力企業への発注の記録 (取適法の対象の取引) は 2 年以上 | 消せない (取り消しても行は残る) |
| 受入 | 「受入」の画面 | 7 年 (欠損金のある年度は 10 年) | 消せない |
| 仕入明細と仕入明細回答 | 「仕入明細」(発注した側) と「受けた仕入明細」(受注した側) の画面。送り合った記録にも残る | 7 年 (欠損金のある年度は 10 年) | 消せない (取り消しても行は残る) |
| 送り合った記録 | 「送り合った記録」の一覧 (設定の画面の「普段は触らない物」から開く) | 7 年 (欠損金のある年度は 10 年) | 消せない (直す道と消す道が無い) |
| 読み取った注文書 (元のファイル) | 「注文書の読み取り」の画面。ファイルは置き場の `media/` | 7 年 (欠損金のある年度は 10 年) | 消せない |
| 添付 | 記録ごとの「添付ファイル」 | 付けた先の記録と同じ | 消せる (行とファイルを消す。消す前に取った控えと外への写しには、その控えを消すまで残る) |

出所: 7 年は、中小企業共通 EDI の EDI インボイス仕様編 6.3.2 の字です (送り合った記録の表の説明 `src/seizou/connect/models.py` が引く資料)。欠損金のある年度の 10 年と、協力企業への発注の記録の 2 年以上の出所は未確認です。作者は、法令の本文と国税庁の資料を読んでいません。

表の中で seizou が消す道を持つ物は、添付だけです。伝票・送り合った記録・読み取った注文書は、seizou に消す道が無く、データベースと控えに残り続けます。

### 月末の控えを外に 7 年置く

上の「外への写し」の restic で、日ごとの写しを 30 日、月ごとの写しを 84 か月 (7 年) 残す例です。`--keep-monthly 84` は、月ごとに最後の写しを 1 つ残す印です。10 年残す年度があるときは、`--keep-monthly 120` にします。

```
restic forget --keep-daily 30 --keep-monthly 84 --prune
```

この 1 行は写しを消すので、消す権限のある鍵が要ります。VPS には書くだけの鍵を置くので、この 1 行は VPS の cron に置かず、VPS の外の PC から月に 1 回打ちます (その PC にも、合言葉と消せる鍵を置きます)。写し先の側の消せない期間は、この残す期間と合わせます。

## 戻す (復元)

戻すと、今のデータベースと上げたファイルが、控えを取った時点の物に置き換わります。次の順に進めます。

1. サーバーを止めます (runserver の窓を閉じるか、サーバーの service を止める)。
2. `<python> manage.py seizou_restore --list` で控えの一覧を出し、戻す控えの名前を選びます。
3. `<python> manage.py seizou_restore <控えの名前>` を打ちます。
4. 「本当に戻しますか?」の問いに `yes` と打ちます。ほかの答えでは何も変えずに止まります。
5. 控えの seizou の版が今より古いときは、`<python> manage.py migrate` を打ちます。
6. `<python> manage.py seizou_doctor` で点検し、直す物があれば直します。
7. サーバーを立てます。

命令は、戻す前の今の物を `backups/<日時>-before-restore/` に控えます。戻したことを取り消すには、同じ命令にその名前を渡します (`<python> manage.py seizou_restore <日時>-before-restore`)。

上げたファイルは、控えの時点の物にそろいます。控えの後に上げたファイルは消えますが、`<日時>-before-restore` の中に残っています。`answers.yaml` は戻しません (置き場の `settings.py` と対の物で、データではないため)。

命令は、別の会社の控えと、データベースの種類が違う控えを戻しません。

PostgreSQL の置き場では、命令は戻さずに、`pg_restore` で戻す 1 行を出して止まります。その 1 行で戻し、上げたファイルは控えの `media/` を `MEDIA_ROOT` (置き場の `media/`) に写してください。

### 戻せるかを確かめる (本番に触らない)

控えから本当に戻せるかは、戻さずに次の命令で確かめます。

```
<python> manage.py seizou_restore <控えの名前> --verify
```

この命令は、本番のデータベースと上げたファイルに触りません。控えのデータベースの写しを一時のフォルダに写し、読むだけで開きます。確かめるのは次の 3 つです。

- 控えのデータベースが開けるか (SQLite の `quick_check`)
- 控えと今のデータベースで、当てた migration に差があるか (版の違いの目安です。差があっても失敗にはしません)
- 控えの上げたファイルの数が、`backup.json` に書いた数と同じか

結果は、控えの置き場の `backups/restore-checks.jsonl` に 1 行残ります (確かめた日時・控えの名前・かかった秒・成否)。データベースが開けないときと、ファイルの数が違うときは、終わりの番号 1 で終わります。サーバーは止めなくてかまいません。

90 日に 1 回を目安に確かめてください。最後に確かめてから 90 日を過ぎると (まだ確かめていなければ、一番古い控えから 90 日)、本番の条件の点検 (`seizou_doctor`) が「直す」の行を出します。

戻すとき (`seizou_restore <控えの名前>`) も、命令は先に同じ確かめをします。控えのデータベースが壊れていれば、何も変えずに止まります。そのときは別の控えを選んでください。

PostgreSQL の置き場では、この確かめは使えません。

## 立ち上げの確かめ (点検)

次の命令で、置き場を点検します。点検は読むだけで、何も書き換えません。

```
<python> manage.py seizou_doctor
```

打つのは、立ち上げた直後、本番にする前 (`--production` を付ける)、版を上げた後、戻した後です。
`seizou new` も、終わりにこの命令の 1 行を出します。

命令は 1 行に 1 つ、`良い  <見た物>: <様子>` か `直す  <見た物>: <様子> → 直し方: <すること>` を出します。最後に「点検の結果: 良い N 件・直す M 件」を出します。直す物が 1 つでもあれば、終わりの番号 1 で終わります (cron や監視の道具が見分けられます)。

見る物は次のとおりです。鍵は、値を出さずに、有るか無いかだけを見ます。

- `SECRET_KEY` (置いてあるか。短すぎないか)
- `.env` の権限 (持ち主だけが読めるか)
- 開発の設定 (`DEBUG`)
- 開発機の自動ログイン (本番の条件だけ)
- `ALLOWED_HOSTS` (ほかの PC から開く名前があるか。本番の条件だけ)
- migrate の漏れ
- Django の起動の検査 (`check`)
- 上げたファイルの置き場 (`MEDIA_ROOT` に書けるか)
- 上げたファイルの置き場の場所 (`MEDIA_ROOT` が置き場そのものか、その親を指していないか。指していれば、控えと戻しは止まる)
- 控えの置き場 (`backups/` に書けるか)
- CSS (seizou の画面の見た目のファイルがあるか)
- `collectstatic` (本番の条件だけ)
- 上げたファイルの配り方 (nginx に渡すときは、`deploy/nginx-files.conf` の `internal;` と alias の道)
- 会社の選べる設定 (`answers.yaml` の `settings` の値が選べる値の中か)
- つながりの鍵 (取引先ごとの鍵の置き場の名前が `.env` にあるか)
- つながりの受け口の URL (`https://` か。本番の条件だけ)
- Cookie が HTTPS だけ (セッションと CSRF の Cookie。本番の条件だけ)
- 最後の控え (36 時間より古いか、置き場を作って 36 時間を過ぎても控えが無ければ直す。本番の条件だけ。直し方は「cron の行を確かめる」と出るが、Windows の PC では、タスク スケジューラに置いた控えの仕事を確かめる)
- ディスクの空き (1GB か最後の控えの 2 倍を切ったら直す。本番の条件だけ)
- 作り物の利用者の合言葉 (公開の合言葉のままの人がいないか。本番の条件では直す)
- AI が守る決まり (置き場の CLAUDE.md と AGENTS.md。無くても止めない)
- 権限の判定 (部署・編集の権限・金額の閲覧が記録だけのままなら、本番の条件では直す。断られる人がいないかを `seizou.access` の記録で確かめ終えたら on にする)
- settings.py の塊 (`LOGGING` と `HtmxLoginMiddleware` の行があるか。本番の条件だけ)
- 決まりの検査 (会社の置き場) (会社の置き場のコードが、書き方の決まり R13〜R19・R22 を破っていないか。違反があれば直す。最初の 1 件の番号とファイルと行を出す。seizou の部品の中は見ない。置き場の `backups/`・`practice/`・`staticfiles/`・`media/`・`cache/` の下は見ない。本番の条件でも開発の条件でも見る)

「本番の条件」は、`.env` の `DEBUG` が 0 のときか、`--production` を付けたときです。開発の設定 (`DEBUG` が 1) のままでは、本番の条件の行を出さずに、その案内を 1 行出します。HTTPS の細かい設定は、`<python> manage.py check --deploy` で見ます。LAN の中だけで使う置き場では、当たらない項目もあります。

## 本番の守り (HTTPS・ログイン・稼働の確認)

本番 (`.env` の `DEBUG=0`) で、seizou が自分で守る物と、置き場で確かめる物です。

### 稼働の確認の口 `/health/`

`/health/` は、ログインを見ずに `{"ok": true}` を返します。データベースは読みません (サーバーが要求に答えるかだけを見ます)。監視の道具や nginx の確かめは、この URL を開きます (例 `curl -fsS https://<このシステムの名前>/health/`)。名前は `.env` の `ALLOWED_HOSTS` にある物を使います (無い名前では 400 になります)。データベースと置き場の確かめは `seizou_doctor` で見ます。

### HTTPS と Cookie

本番では、ログインの Cookie (セッションと CSRF) を HTTPS の道でだけ送ります (`seizou new` が書く `settings.py` の `if not DEBUG:` の行)。nginx で https を受け、Django へ渡す location (`proxy_pass` を書いた所) に次の 3 行を書きます。3 行目は、下の「ログインの締め出し」が接続元を見分けるための行です。

```
proxy_set_header Host $host;
proxy_set_header X-Forwarded-Proto $scheme;
proxy_set_header X-Real-IP $remote_addr;
```

LAN の中だけで http で開く置き場では、この形のままではブラウザが Cookie を送らず、ログインできません。その置き場は、`settings.py` の `SESSION_COOKIE_SECURE` と `CSRF_COOKIE_SECURE` の 2 行を消します (点検の「Cookie が HTTPS だけ」は「直す」のまま残ります)。

上の帯の「現品票を読む」(QR のボタン) でカメラを使うのは、https の住所で開いたときだけです (ブラウザの決まり)。http で開く LAN の置き場では、小窓の「指示書」の欄で探します。今までどおり、スマホのカメラのアプリで現品票の QR を読んで開くこともできます。現品票の QR には、刷った時に開いていた住所が入ります。「現品票を読む」は、今開いている住所と同じ住所の現品票だけを開きます。

### ログインの締め出し

ログインの画面で、同じ ID と同じ接続元 (IP) から 5 回続けて失敗すると、15 分の間はその組のログインを受け付けません (正しいパスワードでも)。画面には「ログインに続けて失敗したので、15 分の間は受け付けません。」と出ます。ログインに成功すると、その ID と接続元の組の数を数え直します。

数は、置き場の `cache/login/` のファイルに持ちます (同じ置き場で動く gunicorn の worker と process の全部で 1 か所に数えるので、worker を複数にしても 5 回目で締め出します)。15 分より早く解くには、`cache/login/` の中のファイルを消します (サーバーを立て直しても数は残ります)。置く場所は `settings.py` の `SEIZOU_LOGIN_CACHE_DIR` で変えられます。

nginx の後ろでは、Django から見た接続元 (`REMOTE_ADDR`) がいつも nginx (127.0.0.1) になります。その置き場は、`.env` に `SEIZOU_CLIENT_IP_HEADER=X-Real-IP` の 1 行を足し、nginx の `proxy_set_header X-Real-IP $remote_addr;` (上の「HTTPS と Cookie」の 3 行目) の値を接続元にします。nginx は、外から来た同じ名前の見出しをこの値で上書きします。手前に nginx のような proxy が無い置き場では、この行を書きません (書くと、利用者が見出しで接続元を偽れます)。CDN (Cloudflare など) を通す置き場では、nginx の realip で CDN から来た要求の接続元を取り直してから渡します。

`.env` にこの行を書いた置き場では、同じ接続元からのログインの失敗が 15 分に 30 回になると、その接続元からのログインを 15 分受け付けません (ID を問わず、正しいパスワードでも。画面の字は上と同じです)。15 分は最初の失敗から数え、ログインに成功しても数は消えません。事務所の PC が 1 つの番地からまとめて外に出る形を考えて、ID ごとの 5 回より高くしてあります。この行が無い置き場では、ID ごとの締め出しだけになり (ほかの人が、ある ID を 15 分止めることもできます)、接続元の上限は効かせません。全員が nginx の 127.0.0.1 に見えるので、効かせると外から会社の全員を止められるためです。

ログインの成功と失敗、ログアウト、締め出し、締め出しの間に断ったログインは、サーバーの記録 (`seizou.login`) に 1 行ずつ書きます。行には ID (150 字まで) と接続元が入り、パスワードは書きません。日時は記録の側が付けます。本番では journald に残り、`sudo journalctl -u seizou-<会社の id>` で見ます。再起動の後も残し、残す期間を決める設定は、[vps.md](vps.md) の 2 にあります。

### ログインが切れたときと、2 回押し

一覧の検索や小窓の途中でログインが切れても、画面の一部にログインの画面がはまり込まず、画面の全体がログインの画面に移ります。ログインの後は、元の画面へ戻ります (`settings.py` の `MIDDLEWARE` の `HtmxLoginMiddleware`)。

保存のボタンは、押すと「処理中…」になり、同じ画面から 2 回送りません。htmx で送る欄も、送っている間は送るボタンを押せません。

### 会社どうしの送る先を外の名前に絞る

`settings.py` に `SEIZOU_CONNECT_PUBLIC_ONLY = True` の 1 行を書くと、会社どうしのつながりの送る先を外の名前に絞ります。既定 (書かないとき) は今のままで、名前を引かず、http の URL も通します。会社の設定の画面からは変えられません。

真にすると、次の 2 つが変わります。

- 取引先との接続の「送る」の URL は、`https://` で始まる物だけを保存できます。`http://127.0.0.1` や `http://localhost` も保存できません。
- 送る前に URL の名前を引き、引いた番地のどれか 1 つでも社内か手元の番地 (`10.0.0.5`・`127.0.0.1`・`169.254.169.254` など) なら送りません。返事の欄には「送っていません: 受け口の URL の名前が社内か手元の番地 (…) を指しています。」と出ます。名前が引けないときも送りません。

VPS の置き場で勧めます。入れる前に、VPS の中で相手の名前を引き、外の番地を指すかを確かめます (例 `getent hosts <相手の名前>`)。真にする前に保存した「送る」の URL は、接続の一覧で https かを確かめます (保存し直すまで http のまま残ります)。LAN の中だけで http で開く置き場と、手元で 2 社を立てて送り合う置き場では、この行を書きません (社内の PC の名前と `http://127.0.0.1` へ送れなくなります)。

限り: 名前を確かめた後に、送る道具がもう 1 度名前を引きます。その間に名前の向きを変える攻撃 (DNS rebinding) は止めません。

### ログインの時間切れ

操作しない間が 2 時間を過ぎるか、ログインから 12 時間を過ぎると、次に画面を開いた時にログインの画面へ戻ります。ログインの後は、元の画面へ戻ります (`settings.py` の `MIDDLEWARE` の `SessionTimeoutMiddleware`)。受信した注文の 2 秒ごとの取り直しのような、画面が自分で読み直す動きは「操作」に数えません。開いたまま席を離れると、画面が読み直していても 2 時間で切れます。

時間は、答えの YAML の `settings` の `session_idle_minutes` (操作しない間。分) と `session_max_hours` (ログインからの最長。時間) で変えます。設定の画面からは変えません。

ログインの画面の「ログイン状態を保存する」は、初めは外れています。外れたままログインすると、ブラウザを閉じた時にログインが切れます。付けた人だけ、ブラウザを閉じてもログインが残ります (残るのはログインからの最長の時間までです)。共用の PC では付けません。

## 鍵を入れ替えるとき・漏れたとき・取引をやめるとき

置き場の `.env` の鍵とパスワードは、2 年以内に 1 度と、鍵を知る担当が替わった時に入れ替えます。漏れたときは、すぐ入れ替えます。どの値も、会話・チャット・commit・画面に貼りません (SECURITY.md の「取引先の鍵の作り方」と同じ)。下の例の `<…>` は、自分の値に置き換える所です。

### `SECRET_KEY` (Django のログインと署名に使う鍵)

計画した入れ替えでは、前の値をしばらく残して、ログインしている人を締め出さずに替えます。

1. 自分の端末で `<python> -c "import secrets; print(secrets.token_urlsafe(50))"` を打ち、新しい値を作ります (`seizou new` と同じ作り方です。AI の道具には打たせません)。
2. `.env` の `SECRET_KEY` の行を新しい値にし、前の値を `SECRET_KEY_FALLBACKS` の行に置きます。

```
SECRET_KEY=<新しい値>
SECRET_KEY_FALLBACKS=<前の値>
```

3. サーバーを起動し直します。
4. ログインの最長の時間 (「ログイン状態を保存する」を付けたときの 2 週間。Django の既定の `SESSION_COOKIE_AGE`) が過ぎたら、`SECRET_KEY_FALLBACKS` の行を消して、もう 1 度起動し直します。

`settings.py` に `SECRET_KEY_FALLBACKS` の行が無い置き場 (v0.1.0 までの seizou で作った置き場は、全部これに当たります) は、下の「版を上げる手順」のとおりに足してから進めます。

漏れたときは、`SECRET_KEY_FALLBACKS` を使いません。`SECRET_KEY` を新しい値だけにして起動し直します。漏れた値で作られたログインを残さないためで、全員がログインし直すことになります。

### 取引先の鍵 (`SEIZOU_PARTNER_<相手の会社の id を大文字にした物>_SECRET`)

今の版は、相手ごとに鍵を 1 つだけ持ちます。新しい値と前の値を重ねて持つ仕組みは無いので、2 社で同じ時刻に替えます。

1. 2 社の担当で、入れ替える時刻を決めます。
2. 片方の担当が、自分の端末で `<python> manage.py seizou_secret <鍵の置き場の名前>` を打って新しい値を作り、= の後ろの値を相手の担当へ人の手で渡します (SECURITY.md の「取引先の鍵の作り方」)。
3. 決めた時刻に、2 社とも `.env` のその行を同じ新しい値に直し、起動し直します。
4. 2 社が起動し直すまでの間に送った物は、鍵が合わずに相手に届きません。送った結果の字を見て、届いていない物を送り直します。

### API の鍵 (`ANTHROPIC_API_KEY` の行)

1. Anthropic の Console で新しい鍵を作ります。
2. `.env` の `ANTHROPIC_API_KEY` の行を新しい鍵に直し、起動し直します。注文書の見張りを動かしている置き場は、見張りも止めて立て直します ([intake-watch.md](intake-watch.md) の「止め方と、動いているかの見方」)。
3. 古い鍵を Console で無効にします。

### GitHub のトークン (フィードバックの GitHub の口)

1. GitHub で古いトークンを無効にします。
2. 世話役が「GitHub とつなぐ」の画面で、新しいトークンを置き直します。

### メールのパスワード (`EMAIL_HOST_PASSWORD`)

1. メールのサーバーでパスワードを変えます。
2. `.env` の `EMAIL_HOST_PASSWORD` の行を新しい値に直し、起動し直します。
3. 設定の画面の「試しに送る」で、メールが届くかを確かめます。

### 取引をやめるとき

その取引先の鍵の行を `.env` から消して、起動し直します。送る口も受け口も鍵が合わなくなり、その相手とは送り合えなくなります。今ある取引の記録は、そのまま残ります (取引先を使用停止にしても、記録は消えません)。使用停止にした取引先から届いた物を断る仕組みは、今の版にはありません。

## 版を上げる手順

seizou の新しい版を入れるときは、次の順に進めます。

1. `<python> manage.py seizou_backup` で控えを取ります。
2. サーバーを止めます。
3. seizou を入れ直します。git から入れた人は `cd <seizou を clone した場所> && git pull && uv sync --locked`、PyPI の版を使う人は `uv pip install --python <python> -U seizou` です。`<python>` は、上の「この文書は何か」と同じく、置き場の README の「起動」の 1 行に出てくる Python です。入れる先の Python を名指しするのは、端末の `pip` が別の Python に入れることがあり、uv が作った `.venv` には `pip` が無いためです。本番の VPS ([docs/vps.md](vps.md) の 5 の形) では `uv sync --locked --no-dev --extra pdf --extra server` です。`--extra pdf` が無いと PDF の部品 (weasyprint) が入らず、`--extra server` が無いと本番の Web サーバーの gunicorn が入りません (gunicorn は extra `server` に入っています。v0.1.0 より前に git の main の seizou で作り、gunicorn を別に入れて残す置き場は、`--inexact` も付けます)。
4. `<python> manage.py migrate` を打ちます。
5. `<python> manage.py seizou_doctor` で点検し、直す物があれば直します。
6. 本番で nginx が静的ファイルを配る形なら、`<python> manage.py collectstatic --no-input` を打ちます。
7. サーバーを立てます (runserver の 1 行か、サーバーの service の再起動。手元の 2 社のデモは `uv run python scripts/sites.py restart`)。
8. 画面を 1 つ開いて、ログインと一覧が出ることを確かめます。

版を上げた後に、置き場ごとに `seizou ai-docs <置き場>` を打ちます (git から入れた人は clone した場所で `uv run seizou ai-docs <置き場>`)。この命令は置き場を、プラグインの MCP が起こしてよい置き場の一覧 (`~/.seizou/sites.json`) に、打った python で登録します (登録の無い置き場では、プラグインの MCP は立ちません)。Claude Code に `.env`・DB・控えを読ませない設定 (`.claude/settings.json`) が無い置き場 (v0.1.0 より前に git の main の seizou で作った物) には、それも書きます (既にあれば触りません)。`CLAUDE.md` と `AGENTS.md` が既にある置き場では「止まりました: 既にあります」と出ますが、登録と settings.json はその前に済んでいます。

うまく動かないときは、前の版に戻します。PyPI の版は `uv pip install --python <python> seizou==<前の版>`、git から入れた人は `git checkout <前の tag>` と `uv sync --locked` です。続けて、サーバーを止めてから、`<python> manage.py seizou_restore <1 で取った控えの名前>` で戻します。

点検 (`--production`) の「Cookie が HTTPS だけ」が直すを出したら、`settings.py` に次の行があるかを見ます。行が無い置き場 (v0.1.0 より前に git の main の seizou で作った物) は、版を上げるときに足します。`ALLOWED_HOSTS` の行の後に、次の塊を足します。Cookie の 2 行は、HTTPS で開く置き場だけです (上の「HTTPS と Cookie」)。

```
SESSION_COOKIE_HTTPONLY = True
if not DEBUG:
    SESSION_COOKIE_SECURE = True
    CSRF_COOKIE_SECURE = True
    SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
```

点検 (`--production`) の「settings.py の塊」が直すを出し、`HtmxLoginMiddleware` が無いと書いたときは、`MIDDLEWARE` の `"seizou.core.middleware.DevAutoLoginMiddleware",` の次の行に、`"seizou.core.middleware.HtmxLoginMiddleware",` を足します。この行が無いのは、v0.1.0 より前に git の main の seizou で作った置き場です。

画面ごとの説明書の断片が無い置き場 (v0.1.0 より前に git の main の seizou で、`--demo` を付けずに `seizou new` で作った物) は、版を上げた後に、部品の中の標準の組を置き場の `manual/` に写します: `cp -n <seizou を clone した場所>/src/seizou/core/manual_default/*.html <置き場>/manual/`。`-n` は、同じ名前のファイル (自社で直した断片) を上書きしない印です。

点検 (`--production`) の「パスワードの決まり」が直すを出したら、`settings.py` に `AUTH_PASSWORD_VALIDATORS` の行があるかを見ます。行が無い置き場 (v0.1.0 より前に git の main の seizou で作った物) は、`from seizou.parts import PARTS` の次の行に `from seizou.core.passwords import VALIDATORS as AUTH_PASSWORD_VALIDATORS` を足します。足すのは 3 で seizou を入れ直した後、7 でサーバーを立てる前です (先に足すと、古い seizou にこの部品が無く、起動しません)。足すと `manage.py changepassword` も、アカウント管理の画面と同じ決まり (8 字以上・よくある語でない・数字だけでない・ID に似ていない) で断ります。

ログインの時間切れ (上の「ログインの時間切れ」) は、`settings.py` の `MIDDLEWARE` の 1 行で動きます。この行が無い置き場 (v0.1.0 より前に git の main の seizou で作った物) は、`"seizou.core.middleware.HtmxLoginMiddleware",` の次の行に `"seizou.core.middleware.SessionTimeoutMiddleware",` を足します。この行が無いと、時間切れは働きません。足すのは seizou の版を上げた後で、足したらサーバーを立て直します。先に足すと、古い seizou にはこの名前が無いので、サーバーが起動しません。

点検 (`--production`) の「settings.py の塊」が直すを出し、`LOGGING` が無いと書いたときは、`settings.py` に `LOGGING` の行があるかを見ます。行が無い置き場 (v0.1.0 より前に git の main の seizou で作った物) は、import の並び (`from seizou.parts import PARTS` の次) に `from seizou.core.logging_conf import default_logging` を、`LANGUAGE_CODE` の行の後に `LOGGING = default_logging()` を足します。足すのは 3 で seizou を入れ直した後、7 でサーバーを立てる前です (先に足すと、古い seizou にこの部品が無く、起動しません)。足すと、500 の誤りと seizou の記録がサーバーの記録 (journald) に残ります。

`settings.py` に `SECRET_KEY_FALLBACKS` の行が無い置き場 (v0.1.0 までの seizou で作った置き場は、全部これに当たります) は、`SECRET_KEY = os.environ["SECRET_KEY"]` の行の次に、次の 1 行を足します。足した後に、サーバーを立て直します。この行は seizou の部品を使わないので、版を上げる前に足してもかまいません。この行が無いと、上の「鍵を入れ替えるとき・漏れたとき・取引をやめるとき」で `.env` に書いた `SECRET_KEY_FALLBACKS` を、Django が読みません。

```python
SECRET_KEY_FALLBACKS = [value.strip() for value in os.environ.get("SECRET_KEY_FALLBACKS", "").split(",") if value.strip()]
```

## 会社ごとの項目を立てた後に足す

部品マスターに会社ごとの項目 (例 表面の仕上げ) を、置き場を立てた後に足す手順です。部品の表 (`masters` の `Item`) は変えず、1 対 1 の拡張の表 (`fields/models.py` の `ItemExt`) に列を足します。この手順は、置き場に `fields/` がある会社 (`seizou new` の時に、答えの YAML の `item_fields` に項目を書いたか、業種の見本が項目を補った会社) のための物です。

画面の欄と一覧の列は、置き場の `fields/` の 2 つのファイル (`models.py` と `apps.py`) で決まります。答えの YAML の `item_fields` は、`seizou new` が置き場を作る時に読む物です。置き場の `answers.yaml` を後で直しても、画面は変わりません。

1. 置き場の `fields/models.py` の `ItemExt` に、列を 1 行足します。列の名前は、今ある最後の `ext<番号>` の次の番号にします (例 `ext02` まであれば `ext03`)。字の項目の例です。

```python
    ext03 = models.CharField('表面の仕上げ', max_length=100, blank=True)
```

ほかの型の行は、`seizou new` が書く形に合わせます。`<見出し>` は画面に出る項目の名前です。

- 数: `models.DecimalField('<見出し>', max_digits=14, decimal_places=2, null=True, blank=True)`
- 日付: `models.DateField('<見出し>', null=True, blank=True)`
- 選ぶ物: `models.CharField('<見出し>', max_length=100, choices=[('<値>', '<値>'), ...], blank=True)`
- はい/いいえ: `models.BooleanField('<見出し>', default=False, blank=True)`

2. 同じ置き場の `fields/apps.py` の `ITEM_FIELDS` に、同じ列の 1 行を足します。鍵の並びは、`seizou new` が書いた行と同じです (`name`・`label`・`type`・`required`・`in_list`・`searchable`・`choices`)。上の例の列なら、次の 1 行です。

```python
    {'name': 'ext03', 'label': '表面の仕上げ', 'type': 'text', 'required': False, 'in_list': True, 'searchable': False, 'choices': []},
```

`type` は `text` (字)・`number` (数)・`date` (日付)・`choice` (選ぶ物)・`bool` (はい/いいえ) のどれかで、1 の行の型と合わせます。`in_list` を `True` にすると部品の一覧に列が出ます。`searchable` を `True` にすると、検索がこの列も見ます。`choice` の項目は、`choices` に 1 の行と同じ値を並べます。

3. 置き場で次の 2 つの命令を打ち、サーバーを立て直します。

```
<python> manage.py makemigrations fields
<python> manage.py migrate
```

`models.py` だけを直して `apps.py` を直さないと、編集の画面に欄が出ず、誤りの字も出ません。2 つのファイルを両方直してから、サーバーを立て直してください。

足した列の値はデータベースに入るので、毎日の控えに入ります。`fields/` のファイルは、控えの `site/` に入ります (上の「毎日の控え」)。

## 困ったとき

`manage.py` が `KeyError: 'SECRET_KEY'` で止まるときは、置き場に `.env` が無いか、`.env` に `SECRET_KEY=` の行がありません。`.env` は控えに入らないので、別に写しておいた `.env` を置き場に戻してください。このときは `settings.py` が先に止まるので、点検も動きません。

上げたファイルの画面が 503 で止まるときは、nginx の設定が足りません。画面の案内のとおりに直し、点検の「上げたファイルの配り方」の行を見てください。

どの画面も「決まりに沿っていません」になるときは、開発の設定 (`DEBUG` が 1) で、会社の側のコードが決まりを破っています。画面の文を写して、Claude Code の `/seizou:fix` で直してください。

画面が 500 (サーバーの誤り) になったときは、サーバーの記録に誤りの行が残っています。VPS では `sudo journalctl -u seizou-<会社の id> -n 100`、手元では runserver の窓で見ます。

## 止まったとき (初動)

画面が開かない・保存できない・VPS ごと失ったときは、次の 6 段の順に進めます。

1. 気づく: 点検 (`seizou_doctor` が終わりの番号 1 で終わる)、`/health/` が `{"ok": true}` を返さない (上の「稼働の確認の口」)、利用者の声 (画面が開かない・保存できない) のどれかで気づきます。
2. 止める範囲を決める: 止まったのが 1 社だけか、2 社ともかを見ます。同じ VPS に置いた 2 社は、VPS の障害で一緒に止まります。戻すまで、止まった会社では画面から入れないよう、社内に伝えます。
3. 知らせる: 社内と取引先に、止まったことと戻る見込みを知らせます。連絡先の表 (社内の担当・取引先の窓口・VPS を借りた先) は、公開のリポジトリに書かず、VPS の外に作って紙でも持っておきます (会社ごとの名前を公開のリポジトリに書かない決まり。[vps.md](vps.md) の「この文書は何か」)。
4. 紙と電話で続ける: 止まっている間の受注・発注・出荷・受入は紙に書き、取引先とは電話でやり取りします。紙の分は、戻した後に手で入れます。
5. 戻す: 置き場が残っていれば、上の「戻す (復元)」の段で戻します。VPS ごと失ったときは、上の「外への写し」の「写しから戻す」で戻します。
6. 記録する: いつ気づいたか、何が起きたか、どの控え (日時) まで戻したか、何を手で入れ直したかを書き残します。

失う量の見込み (RPO) は 2 段です。失う量は、ディスクの一部の故障なら最悪 1 日分 (毎晩の控えの間) で、VPS ごと失ったときは最後に外へ写した控えの日時から後の分です。

戻すまでの時間 (RTO) は、まだ測っていません。会社の置き場で 1 度戻して測り、次の表に書き込みます。

| 戻した形 | 測った日 | 戻すまでの時間 |
|---|---|---|
| 置き場の控えから (上の「戻す (復元)」) | 未測定 | 未測定 |
| 外への写しから (新しい VPS に) | 未測定 | 未測定 |

### 戻した後の突き合わせ

控えの日時より後に取引先と送り合った分は、戻したデータベースにありません。相手の画面では、届いた物が済んだ形で残っているので、相手に「再送」を押してもらう形では戻りません。次の順に突き合わせます。

1. 取引先に、送り合った記録の一覧の「CSV」で、控えの日時より後の行を書き出してもらいます。
2. こちらの送り合った記録の一覧 (設定の画面の「普段は触らない物」から開く) と比べます。こちらに無い行が、戻して消えた分です。
3. 消えた分を取引先に電話で確かめ、手で入れ直します。相手には既に届いているので、入れ直した発注をもう一度送るかは、相手と電話で決めます。

## 定期の仕事と見張り

システムを預かる人が、決まった間隔でする仕事です。cron に置く物は、控えと同じ利用者の cron に足します。Windows の PC では、cron の代わりに、上の「Windows の PC で、毎晩の控えと毎朝の点検を回す」の形でタスク スケジューラに置きます。

| 仕事 | いつ | どうやって | 見落としたとき |
|---|---|---|---|
| 毎晩の控え | 毎晩 | 上の「毎日の控え」の節の cron の 1 行 | その日の分を戻せない。`backups/backup.log` と `seizou_restore --list` の日付で、取れたかを見る |
| 外への写し | 毎晩 (控えの後) | 上の「外への写し」の節の cron の 1 行 | VPS ごと失ったとき、最後に写した日から後を失う。`restic snapshots` の日付で見る |
| 点検 | 毎日 (例) | `<python> manage.py seizou_doctor` を cron で打つ。直す物があると終わりの番号 1 で終わるので、外の見張りで拾える | 鍵の権限や設定のずれに気づかない |
| 古いセッションの掃除 | 週に 1 回 (例) | `<python> manage.py clearsessions` を cron で打つ | 切れたログインの行が、データベースに溜まり続ける |
| 古い控えの削除 | 上の「毎日の控え」の節のとおり | 上の「毎日の控え」の節の、古い控えの段 | ディスクが埋まり、控えを取れなくなる |
| 記録のファイルの回し | 週に 1 回 (OS の logrotate) | 下の logrotate の例 | `backups/backup.log` が大きくなり続ける |
| 証明書の残り日数 | 月に 1 回 (例) | 更新は certbot の timer がする ([vps.md](vps.md) の 13)。`sudo certbot certificates` で残りの日数を見る | 証明書が切れ、画面と取引先からの送りが https で通らなくなる |
| 外から `/health/` を見る | 数分ごと | 外から URL を数分ごとに開いて知らせる見張り (VPS の外に置く) で、`https://<このシステムの名前>/health/` を開く | 止まったことに、利用者の声まで気づかない |

記録のファイルの回しの例です (`/etc/logrotate.d/seizou`。道は例。作者の手元では未確認)。

```
/path/to/site/backups/*.log {
    weekly
    rotate 8
    compress
    missingok
    notifempty
}
```

### 時刻の帯

cron は OS の時刻で動きます。VPS の OS が世界の標準の時刻 (UTC) のままだと、「毎晩 2 時」の控えは日本の 11 時に動きます。`timedatectl` の `Time zone` の行で OS の時刻帯を見て、日本の時刻でなければ、次のどちらか 1 つにします。

- OS を日本の時刻にする: `sudo timedatectl set-timezone Asia/Tokyo`
- cron の頭に次の 1 行を書く (その後に書いた cron の行が、日本の時刻で動く)

```
CRON_TZ=Asia/Tokyo
```

## 打ち間違えたとき (出荷・受入・在庫)

出荷の数量・出荷日・備考を打ち間違えたときは、出荷の一覧の行の ⋮ か右クリックの「編集」で直します。違う受注の明細へ入れた出荷と、二重に入れた出荷は、同じメニューの「削除」で消してから、正しい受注の明細へ出荷し直します。消すと、受注の状態と在庫の数は出荷の前に戻ります。消した事は変更の履歴に残ります。

次の出荷は消せません。削除の小窓には、消せない訳と次にすることだけが出ます。

- 発行の納品書に入った出荷は、先に納品書を取り消します。
- 請求書の明細か、請求書の外の入金の記録が指す出荷は消せません。請求書や入金を取り消しても、その記録は出荷を指したまま残ります。数や日付の誤りは「編集」で直します。
- 明細を出し終えた出荷 (一式の明細なら、一式の金額が付く出荷) は消せません。数や日付の誤りは「編集」で直します。

発行の納品書に入った出荷は、納品書を取り消す、出荷を直すか消す、納品書を作り直す、の順に直します。納品書を取り消す操作と作り直す操作は金額の操作なので、金額の判定を有効にした会社では、金額を見られる人だけが行えます。

請求書に入った出荷 (一式の行で請求した明細の出荷と、請求書の外で入金を受け取った出荷も含む) を直すか消すとき、その出荷の入った納品書を取り消すときは、会社の設定 (R27) に従って、黄色の知らせが出るか、赤の知らせで止まります。直しても請求書の明細の数量は変わらないので、請求書も直すときは、請求書を取り消して作り直します。

取引先につながる出荷は、受信した注文で作った受注の出荷・出荷の知らせを送った出荷・検収の届いた出荷の 3 つです。どれも消せません。出荷の知らせを送り直しても、相手の記録は 1 回目の数のまま残ります。数の誤りは、受注の詳細の「会話」のタブで相手に伝えてください。この出荷の直し方は、まだありません (これから設計します)。

受入は、保存した後に画面から直せません。数の誤りは、運用で見つけて直します。受入の金額の誤りは、相手が seizou を使う協力企業なら、相手が仕入明細に出した提案を受け入れて、修正仕入明細の金額で直せます (受入の行の金額は変わりません)。ほかの取引先では直せません。受入の数と日付と在庫の入庫は、どちらの場合も誤ったまま残ります。

在庫の数が実地の数と合わないときは、在庫の一覧の行の ⋮ の「棚卸しの調整」で実地の数に合わせます。

実績 (進捗) を打ち間違えたときは、進捗の盤の行の ⋮ か右クリックの「実績を直す・消す」で実績の一覧へ移り、行の「編集」か「削除」で直します。

## 練習モード (本番に残らない練習用のサーバー)

練習モードは、新しく入った人の練習や、手順の確かめに使います。今のデータベースと上げたファイルの写しを使うサーバーを、本番のサーバーを止めずに、別のポートで立てます。練習の画面での登録・変更・削除は写しにだけ入り、本番には残りません。練習のサーバーでは、全部の画面の上に黄色の帯「練習モード」が出て、ブラウザの題の頭に「練習:」が付きます。

### 立て方

置き場で次の命令を打ち、出た URL をブラウザで開きます。

```
<python> manage.py seizou_practice start
```

ポートの既定は、会社のポートに 100 を足した番号です (例 8001 の会社は 8101)。`--port <番号>` で変えられます。開けるのは同じ PC のブラウザだけです (127.0.0.1)。開発の設定 (`.env` の `DEBUG` と `SEIZOU_DEV_AUTO_LOGIN` が 1) の置き場では、本番と同じく自動ログインで開きます。

命令は、置き場の `practice/` の下に日時の名前のフォルダを 1 つ作り、写しと記録を置きます。写しの取り方は控え (`seizou_backup`) と同じで、本番のサーバーが動いている間でも取れます。

### 止め方

練習が終わったら、次の命令で止めます。

```
<python> manage.py seizou_practice stop
```

命令は、自分が立てた練習のサーバーを止めて、写し (`practice/` の下のフォルダ) を消します。写しは自動では消えないので、練習が終わったら必ず止めてください。立っているかは `<python> manage.py seizou_practice status` で見ます。

### 注意

- 練習のサーバーには、取引先とのつながりの鍵 (`SEIZOU_PARTNER_<相手の id>_SECRET`) を渡しません (空の値にして立てる)。練習の画面で発注を保存する・受信した注文を受け入れる・出荷しても、相手の会社には送られず、「鍵が無い」の知らせになります。相手に送る練習はできません。
- 注文書の読み取りと AI チャットも、本番と同じ鍵で API を呼びます (費用がかかります)。
- 練習モードは SQLite の置き場だけで使えます。PostgreSQL の置き場では、控え (`seizou_backup`) を別のデータベースに戻し、別のサーバーとして立ててください。
- 練習のサーバーは同じ PC の 127.0.0.1 だけで待つので、VPS など nginx の後ろの置き場では、ブラウザから練習の画面に届きません。練習は手元の PC の置き場で行うか、ssh のポートの転送が許されている置き場で、転送した先を開いてください。

### この版より前に作った置き場

`settings.py` に次の塊が無い置き場 (v0.1.0 より前に git の main の seizou で作った物) では、`MEDIA_ROOT = BASE_DIR / "media"` の行の後に、次の塊を足してから使います。

```python
# 練習モード: manage.py seizou_practice start が立てるサーバーだけが、写した DB と上げたファイルの道を渡す。
# cookie の名前も分ける (同じ PC で開いた本番の画面と、ログインと CSRF の cookie が混ざらないように)。
if os.environ.get("SEIZOU_PRACTICE_DB"):
    DATABASES["default"]["NAME"] = os.environ["SEIZOU_PRACTICE_DB"]
    MEDIA_ROOT = os.environ["SEIZOU_PRACTICE_MEDIA"]
    SESSION_COOKIE_NAME += "_practice"
    CSRF_COOKIE_NAME += "_practice"
```

塊の無い置き場では、命令は練習のサーバーを立てずに止まり、取った写しを消します。塊が無いまま立てると、練習の帯を出したまま本番のデータに書いてしまうためです。
