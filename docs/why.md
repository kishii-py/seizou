# seizou の背景 (誰の何のため・既にある道具との違い)

読み手: seizou が自社に合うかを考えている方。作者の見方と、既にある道具との違いを書く。入口は [README](../README.md)。

町工場や中小の製造業が、1 つの命令で自社専用のシステムを持ち、部品マスターを中心に社内の情報を 1 つにつなぎ、同じ仕組みで会社どうしもつながる。日本の企業の 99.7%、336.5 万者が中小企業である ([中小企業庁「中小企業・小規模事業者の数」](https://www.chusho.meti.go.jp/koukai/chousa/chu_kigyocnt/2023/231213chukigyocnt.html)、2021 年 6 月時点)。その受注側で電子受発注に対応しているのは 48.5% ([中小企業庁「令和 3 年度 取引条件改善状況調査」](https://www.chusho.meti.go.jp/keiei/gijut/digitalization/index.html)、2021 年) で、企業間取引の電子化率は 40.0% ([経済産業省「令和 5 年度 電子商取引に関する市場調査」](https://www.meti.go.jp/press/2024/09/20240925001/20240925001.html)、2023 年の値) にとどまる。対応していても画面は得意先ごとに違い (Web EDI の多画面問題)、残りの注文書は紙と FAX で届く。どちらも受けた人が自社の帳簿や表計算に写し直している。

動かす人は、工場の中で Excel と PC を任された 1 人。プログラムは書けなくてよい (Claude Code のプラグイン `/seizou:build` で立てるときに端末に打つのは、入れる 1 行と起動の 1 行の 2 か所。Python の命令 `seizou new` で立てるときは、[「触り方」](getting-started.md)のとおり数行)。詳しくは下の「誰の何のため」。

seizou は 1 つの命令で自社専用のシステムを持つための道具として作っている。自社専用なので、汎用のパッケージより柔軟に、多くの自社の業務を効率化できる。その柔軟さの根拠は 2 つで、会社ごとの項目を本物の列として足せる仕組みと、会社によって向き不向きが分かれる動き (分納を許すか、受注より多い出荷を止めるか、など) を選べる設定である。そのうえで、部品マスター (品番・品名・図面など、部品の情報を 1 か所に持つ表と画面) を社内の情報の唯一の正しい置き場にして、情報をつなぐ。さらに自社の中にとどまらず、同じ仕組みどうしで会社の間の情報もつなぎ、中小企業のネットワークがつながって力を合わせられるようにする。

社内では部署ごとに情報が分かれ、担当者の頭の中にしかない。会社の間では取引先ごとに項目と書式が違い、その違いを人が覚えて吸収している (作者の見方)。

既にある道具とは次の点で違う。汎用の販売管理や生産管理のパッケージは項目と流れが決まっていて、会社ごとの違いは運用で吸収する。得意先ごとの Web EDI は得意先の数だけ画面があり、受けた側が自社の帳簿に写す。システム会社への作り込みは 1 社の中だけで完結し、ほかの会社とは別の形になる。公開の ERP (Odoo や ERPNext など) は業種を問わない汎用の形で、会社ごとの違いは module や設定で足す。日本の町工場の受発注の項目 (中小企業共通 EDI を元にした物) と、番号つきの決まりとテストの 1 対 1 は持たないと作者は見ている (11-08 時点の見方)。seizou は会社ごとの項目を本物の列として足し、向き不向きの分かれる動きを設定で選び、同じ仕組みを入れた会社どうしで同じ形のまま送り合う所が違う (相手も seizou を入れることが前提。相手が入れていない間は、注文書の読み取りと社内の 1 つの形が自社だけの得になる)。

作者が製造業で学んだことが 1 つある。業務の決まりは、なぜそうするかが分からないと、引き継いだ人は変えてよいか判断できず、改善が止まる。だから seizou は、止める処理や端数の丸めのような決まりを実装した関数に「訳」(何のためか、法令・商慣習・作者の決めのどれから来たか、変えてよい条件) を書き、変えたい人がその訳に対して Issue で議論できる形にする (書き方の決まり R22)。訳をまだ確かめていない決まりは「未確認」と書いて残し、埋めることも皆で育てる対象にする。

## 誰の何のため

動かす人として、工場の中で Excel と PC を任された 1 人を考えている。プログラムは書けなくてよい (Claude Code のプラグイン `/seizou:build` で立てるときに端末に打つのは、入れる 1 行と起動の 1 行の 2 か所。Python の命令 `seizou new` で立てるときは、[「触り方」](getting-started.md)のとおり数行)。相手の会社が seizou を入れていなくても、今日の得になる物が 3 つある = 注文書の読み取り (1 枚 約 2.6 円の実測)・部品と取引先の CSV の取り込み (Excel の Shift_JIS のまま)・社内の情報が部品マスターを軸に 1 つの形になること。

作者が働いていた表面処理の工場では、多い日に 1 日 70 件の注文 (紙と FAX で 20 枚、最大の得意先からデータで 50 件) を受け、月 1,400 枚の伝票を手で入れていた。作者は自分の町工場の生産管理システムを作り、複数の中小製造業にも 1 社ずつ作り込んで入れてきたが、同じやり方では全部の町工場に届かない。seizou はその経験で分かった「町工場に要る物」を会期中にゼロから部品の組として書き、1 つの命令で自社専用のシステムを持てる形にし、同じ仕組みで会社どうしもつなぐ。得意先ごとに別の ID で Web EDI に入り直す「多画面問題」には、受注と発注の項目を中小企業共通 EDI を元にそろえ、seizou どうしなら注文と注文回答と出荷の知らせを同じ仕組みで送り合える形で応える。つながる会社が増えるほど、入り直す画面が減る。手で打たずに受けた明細は 1 行 1 分 (設定 `transcription_minutes_per_line` で変えられる) で数え、ダッシュボードに「≒ 転記 m 分」として出す。

作者は表面処理の工場の生産管理に 7 年いた。入出荷と納期の調整を受け持ち、その中で自社のシステムを独学で作った。機械加工や鋳造など複数の中小製造業にも統合基幹システムを入れ、7 つのシステムを並行して運用している (時期は生産管理の 7 年と一部重なる)。情報処理安全確保支援士の資格を持つ。ここまでの経験は会期の前の物で、このリポジトリのコードは会期中に書いた。複数の会社に入れた経験から、具体的な画面を作る前に抽象化の形を決め、その設計を会期中に `core` (ほかの Django の部品が使う土台) として書いた。画面はその上にだけ書き、決まりの検査 (コードの書き方を起動時と CI で調べる仕組み) がその形を守る。チームのもう 1 人は画面を通しで確かめる役と動画を受け持つ。デバッグの経験が豊富だ。会期後の使い所は、受注から請求までの生産管理と、取引先との送り合い。動かすのも、直した版を入れるのも、工場で Excel と PC を任されたその 1 人 (入れ方は[「毎日の運用」](production.md))。世話役 (GOVERNANCE.md) は会社の人ではなく、OSS の側で PR を受け入れて直した版を出す役。

### seizou が選んだ形

町工場が自分で入れて自分で直せるように、4 つを選んだ。

1. 入れ方: `seizou new` の 1 つの命令で、日本語の画面と画面ごとの説明書つきのシステムができて動き出す。作り物の 2 社 (機械加工と表面処理) のデータが入った形でも作れるので、入れた直後から、受注から出荷と納品書と請求書までと、2 社の間の注文の送り合いを通して試せる。
2. 直し方: 会社ごとの違いは拡張の表と設定とテンプレートと会社の検査に置き、部品の表は変えない (R16・R20)。決まりの検査 (R13〜R19 と R22) が機械で守り、置き場の CLAUDE.md が AI にも同じ決まりを守らせる。だから部品の版を上げても、自社で直した所は残る。
3. つながり方: 受注と発注の項目を中小企業共通 EDI を元にそろえ、seizou どうしなら注文・注文回答・出荷の知らせを同じ仕組みで送り合う。会社の中と会社どうしが 1 つの形。
4. 育て方: 使う人のフィードバックが取引先の名前と金額を伏せた Issue の文になり、世話役が読むのは、RULES.md の日本語の差分 (どの決まりが足された・変わったか)、機械が出す一覧 (決まりの番号とテストの対応・検査を黙らせた数・CI と hook と依存の変化。この一覧を出す仕組みは会期後に作り、それまでは同じ項目を世話役が手で確かめる)、決まりのテスト (`tests/test_r*.py`) の差分の 3 つだけ。直した版を入れた会社には「あなたのフィードバックから直しました」の知らせが出る。
