## これからの道筋

これからは、現場の声を次の順に直した版へつなぐ。会社の人が画面の「フィードバック」に困りごとや要望を書くと、取引先の名前と金額らしい数を「〇〇」に伏せた Issue の文ができる。アカウント管理の権限がある人がその文を確かめて「GitHub に送る」で Issue にし (トークンが無い会社は手で写す)、世話役 (GOVERNANCE.md) が直した版を出す。各社は[「毎日の運用」](production.md)の版を上げる手順でその版を入れる (Issue と PR は受け付けている)。

直した版を入れた会社で、アカウント管理の担当者が元のフィードバックの詳細で「直したと記録する」を押すと、書いた人が次にログインしたときに「あなたのフィードバックから直しました」の知らせが 1 回出る。

これから作る物 (命令と手順) は次の 5 つ。確かめる物 (日本語の Windows の実機で手で通した確認・Claude Security の残りの走査・部品の版を上げた実例) は、上の「今の状態」の 6 つに書いた。

- VPS へ立てる命令 (nginx の設定を外から確かめる命令を含む)
- SQLite の控えから PostgreSQL へ入れ直す手順 (VPS の 2 社の置き場は SQLite で立てる = [docs/vps.md](vps.md)。利用者と注文が増えて重くなった会社が、控えを取ってから移る)
- 2 段階の確認 (ログインのときの 2 要素認証)
- 依存を上げて試験を回し、再起動するまでを 1 つにした命令 (版を上げる手順は、今は [docs/operations.md](operations.md) に手で進める形である)
- 外から届く URL を持たない会社どうしをつなぐ中継

### 共通の部品を育てる流れ

会社の人が Claude Code で足した機能は、次の流れで共通の部品に入る。

1. 足した人が PR を出す (CONTRIBUTING.md の Issue の型に沿う)。
2. CI (GitHub Actions。試験を回す sqlite・postgres・windows の 3 本と、依存の見張りの audit、フィードバックの Issue にラベルを付ける feedback-issues) が、ruff・自動テスト・migration の差分の無さ・空の DB への migrate・決まりの検査 (`seizou_check` = R13〜R19 と R22)・CSS の作り直しの一致を回す。通らない PR は入らない。
3. 世話役 (GOVERNANCE.md) が読むのは、RULES.md の日本語の差分と、機械が出す一覧 (決まりの番号とテストの名前の対応・黙らせた数) と、決まりのテスト (`tests/test_r*.py`) の差分だけ。それ以外のテストのコードは読まない。受け入れの基準は誰の PR にも同じ。
4. 入った物は版になり、各社は[「毎日の運用」](production.md)の版を上げる手順で入れる。会社ごとの違いは拡張の表 (R16。部品の表を変えない) と選べる設定で吸収するので、共通の部品を上げても自社の項目と動きは残る。
5. 使う人の「フィードバック」は、取引先の名前と金額を伏せた Issue の文になり、アカウント管理の権限がある人が Issue に送る (トークンが無い会社は手で写す。上の段落)。

作り手が 1 人の社内システムは、その人が離れると直せなくなる。経済産業省の DX レポート (2018 年 9 月) は、古いシステムを刷新できない場合に 2025 年以降、最大 12 兆円/年 (現在の約 3 倍) の経済損失が生じる可能性を「2025 年の崖」と呼んだ。また、保守・運用が属人的となり継承が難しいと考える事業者が 6 割以上と示した ([DX レポートのサマリー](https://www.meti.go.jp/policy/it_policy/dx/20180907_01.pdf))。seizou は部品を共通の OSS で育て、会社の違いを拡張の表と設定とテンプレートに置き、置き場の CLAUDE.md で AI にも同じ決まりを守らせるので、作り手が替わっても引き継げる。
