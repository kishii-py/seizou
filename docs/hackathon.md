## Claude Code でどう作ったか

製品の中で Claude を使う所と、選んだ理由は次の表のとおり (開発で使う Claude Code は下の表)。

| 所 | model か機能 (設定の鍵) | 選んだ理由 | 人が守る所 |
|---|---|---|---|
| 注文書の読み取り | claude-opus-5-5 (`intake_model`) | 読み取りは精度が要る | 人が明細を確かめて「受注登録」を押すまで受注にならない |
| AI チャット | claude-sonnet-5-5 (`assistant_model`) | 速さを優先 | 受注の登録や出荷は提案のカードになり、人が「承認」を押すまで保存しない |
| フィードバックの聞き取り | claude-haiku-5-5 (`feedback_model`) | 聞き取りと仕分けだけなので安い | 下書きは会社の中に残り、GitHub にはアカウント管理の権限がある人が送る (トークンが無い会社は手で写す) |
| 手元の Claude Code からの操作 | MCP サーバー (`manage.py seizou_mcp`) | 画面と同じ `services` と決まりを通す | 書く道具は利用者を決めたときだけ。知らせる設定のポカよけに当たったときは `confirm=true` が要る |

このリポジトリのコードと文書は、会期中に Claude Code で書いた。生産管理の当事者だった作者が、会期の 1 週間で、19 の部品と 159 の画面と決まり 24 本を持つ基幹システムの土台を書き、2 社をつないだ。会期中のチームは 2 人で、Claude Code (model は主に Claude Fable 5.1 と Claude Opus 5.5) と一緒に作った。Mac は 2 台で、1 台は作者の手元にあり、仕様から依頼書を書く会話と、枝を main に取り込む会話を動かす。もう 1 台は会社に置いた常時稼働の Mac で、夜は依頼書 1 本ずつで動く無人のレーンがそこで走る。その記録が `docs/nights/` にある (読み方は [docs/nights/README.md](nights/README.md))。作り方は次の 4 段の繰り返し。

1. 本体の会話 (作者と Claude Code の会話) が、仕様から依頼書を 1 本ずつ書く。依頼書には書いてよいファイルの表・守ること・採用の条件 (機械で確かめる grep と試験) を書く。
2. 別の Mac の無人のレーンが依頼書を 1 本ずつ受け、git の作業場を分けて、依頼書の範囲だけを作り、手元の commit で止まる。
3. 本体の Mac が門 (差分の範囲・禁止語・テスト・書き方の検査・決まりの検査・migration・CSS の作り直し) を通った枝だけを main に取り込む。通らない枝は取り込まず、main を戻す。
4. 作者が朝に、差分と決まりの一覧とテストの結果を見る。

会期中の取り込みは 462 回 (本体の Mac で枝を main に入れる会話 (取り込み係) の記録 `docs/nights/<日付>.md` の番号。11-08 13:10 ごろの main 508b054e)、レーンの記録は 369 本、Claude との共著の印が付いた commit は 2,990 (同じ時点)。

### 作り方 (会期中の回し方)

作者と Claude Code の会話 (本体) で、何を作るかと業務の決め (訳) を決める。手を動かす仕事は、触ってよいファイルの一覧 (`.allow`) を付けた依頼書にして、会社に置いた別の Mac の無人の Claude Code (レーン) に渡す。戻った枝は本体が門 (差分が一覧の中だけか・禁止語・ruff・決まりの検査・全体の pytest・E2E) で見てから main に入れる。1 commit は 1 つの直しで、依頼書ごとの記録と門の記録を `docs/nights/` に毎晩残す。計画と仕様の文書はこのリポジトリの外に置き、コードは会期中にここでゼロから書いた。
